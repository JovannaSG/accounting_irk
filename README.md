# Прототип: ИИ-Аудитор 1С

Прототип приложения для аудита бухгалтерских баз без интеграции с 1С.
Проверки выполняются по загружаемой оборотно-сальдовой ведомости (ОСВ).

## Реализованные проверки (ТЗ §4)

| № | Проверка | Уровень |
|---|----------|---------|
| 4.1 | Красное сальдо (активный счет с кредитовым/отрицательным остатком) | error |
| 4.2 | Развернутое сальдо (одновременно Д и К по одной аналитике/контрагенту) | warning |
| 4.3 | Незакрытое сальдо на конец месяца (закрываемые счета) + зависшее сальдо между периодами (опционально, по умолчанию выкл.) | error / warning |
| 4.4 | Остатки на служебном счете 000 | error |
| 4.5 | Незакрытые расчеты с контрагентами (по реестру документов или эвристике) | error / warning |

Каждую из проверок 4.1–4.5 можно отключить в боковой панели
(в коде — параметром `AutoAuditor1C(..., checks={"red_balance", ...})`; ключи:
`red_balance`, `expanded_balance`, `unclosed_month_end`, `account_000`, `settlements`).

## Дополнительные возможности ядра

- **Ожидаемый документ в 4.5**: в комментарии к незакрытым расчетам указывается,
  какой документ ожидается для закрытия остатка — «ожидается оплата по отгрузке от
  <дата> на <сумма>» или «ожидается отгрузка/зачет по авансу от <дата> на <сумма>».
- **Период возникновения**: для 4.1 и 4.3 в комментарий добавляется период, с которого
  появилось отрицательное/незакрытое сальдо («отрицательное сальдо с <период>»,
  «остаток с <период>»).
- **Контроль групп счетов (расширенный 4.3)**: флаг `balance_group_checks=True`
  (чекбокс в UI) ищет незакрытые остатки по группам: авансы (60.02/62.02/76.АВ/76.ВА),
  РБП (97), товары (41/43), денежные средства (50–58), кредиты (66/67).
- **Рекомендации**: каждой находке соответствует текст рекомендации (ТЗ п.13) —
  виден в сводном отчете, в Excel и в PDF.
- **Реквизиты отчета**: организация и период передаются параметром
  `meta={"organization": ..., "period": ...}` и попадают в шапку отчета (Excel/PDF).
- **PDF-отчет**: `AutoAuditor1C.to_pdf()` формирует печатный отчет (нужны `fpdf2`
  и шрифт DejaVu — `fonts-dejavu-core`, в Docker устанавливается автоматически).

## ML-проверки (аномалии и дубли)

Помимо жестких правил из ТЗ, ядро умеет искать статистически подозрительные места
(все проверки — unsupervised и детерминированные, без обучения моделей):

| Проверка | Что ищет | Источник данных |
|----------|----------|-----------------|
| ML: нетипичная сумма операции | Операция, чья сумма выделяется по истории контрагента (медиана + MAD, порог `k` и минимальная сумма настраиваются) | Реестр документов |
| ML: резкий скачок оборотов между периодами | Рост/падение оборотов (Д и К) по счету между соседними периодами сильнее порога (нужны данные за 2+ периода) | ОСВ |
| ML: возможные дубли контрагентов | Похожие названия: «ООО Ромашка» vs «Ромашка, ООО» — нечеткое сравнение с неважным порядком слов (`rapidfuzz`, порог сходства %) | Субконто ОСВ + Контрагент документов |

ML-проверки включаются в боковой панели (по умолчанию включены), попадают в сводный
и детальный отчет и в выгрузку Excel (уровень «предупреждение» — желтая подсветка).
В коде их можно отключить параметрами `AutoAuditor1C(..., ml_enabled=False)` — это
поведение по умолчанию, поэтому существующие проверки и тесты не меняются.
Детали реализации — в `core/ml.py`.

## NLP-проверка назначений платежей (115-ФЗ)

Отдельная rule-based проверка (`core/nlp.py`): если в реестре документов есть колонка
«Назначение», программа ищет в ней рискованные формулировки по категориям:

| Категория | Примеры маркеров |
|-----------|------------------|
| Обнал | «обнал», «обналичивание», «кэш» |
| Комиссии и переводы | «комиссия за перевод», «перевод собственных средств» |
| Пожертвования | «благотворительная помощь», «пожертвование», «спонсорская» |
| Займы без договора | «займ»/«заём» без номера договора рядом |
| Расплывчатое назначение | «за услуги/товары» без ссылки на документ |
| Третьи лица / прочее | «за третьих лиц», «по просьбе», «возврат ошибочно перечисленных» |
| Наличные | «за наличный расчет», «наличными средствами» |

Категория риска указывается в начале комментария находки («[Обнал] …»). Находки имеют
уровень «предупреждение». Проверка включается чекбоксом «NLP: назначения платежей
(115-ФЗ)»; при отсутствии колонки «Назначение» она тихо пропускается.
В коде: `AutoAuditor1C(..., nlp_enabled=True)` (по умолчанию включена),
свои ключевые слова — `core.nlp.detect_payment_risks(docs, extra_keywords=[...])`.

## Форматы входных данных

**ОСВ (обязательный файл):** CSV, XLS, XLSX, HTML.

- Реальная выгрузка из 1С: отчет «Оборотно-сальдовая ведомость» → «Файл» → «Сохранить как» → Excel или HTML.
  Парсер понимает многострочный заголовок (Сальдо на начало / Обороты / Сальдо на конец × Дебет/Кредит),
  строки субконто (аналитика наследует родительский счет), коды с буквами (`76.АВ`),
  отрицательные (красные) остатки и итоговые строки (`Итого`, `Total`).
- Поддерживается ОСВ с колонкой «Показатели» (БУ/НУ/БУ-НУ, валютные субконто `CNY`, `руб.`):
  аудит использует только данные бухгалтерского учета (БУ), строки НУ/БУ-НУ и валютные (`Вал.`)
  отбрасываются автоматически. Учитывайте: в такой ведомости субсчета (68.01…76.АВ) часто свернуты
  в итог счета, поэтому часть проверок (4.2/4.3/4.5) найдет меньше строк, чем в развернутой ОСВ.
- **MXL не поддерживается** (проприетарный бинарный формат 1С) — сохраните отчет как Excel/HTML.
- Простой CSV (в т.ч. устаревший формат из 2 колонок `Счет,Субконто,Тип,Дебет,Кредит`):

```csv
Период,Счет,Субконто,Тип,НачалоДебет,НачалоКредит,ОборотДебет,ОборотКредит,КонецДебет,КонецКредит
2026-01-31,60.01,"ООО ""Ромашка""",AP,0,0,45000,30000,45000,30000
```

- `Тип`: `A` (активный), `P` (пассивный), `AP` (активно-пассивный).
  Для файлов 1С Тип определяется по плану счетов (встроенный соответствует плану
  счетов 1С:Бухгалтерия 8 ред. 3.0 + настройка «План счетов: Тип»),
  для неизвестных счетов — эвристикой по остаткам.

**Движения/документы (опционально, для проверки 4.5):**

```csv
Дата,Документ,Контрагент,Счет,Вид,Сумма
2026-01-10,Отгрузка №1,"ООО ""Ромашка""",62.01,отгрузка,150000
```

Виды операций: `отгрузка`, `оплата`, `аванс` (принимаются синонимы: реализация, платеж, предоплата...).

Опциональная колонка **Назначение** (алиасы: «Назначение платежа», «purpose») включает
NLP-проверку формулировок платежей (115-ФЗ) — см. соответствующий раздел выше:

```csv
Дата,Документ,Контрагент,Счет,Вид,Сумма,Назначение
2026-01-10,Оплата №1,"ООО ""Ромашка""",60.01,оплата,150000,Оплата по счету №45 от 10.01.2026
```

## Подключение к 1С:Фреш через OData (опция)

Облачный сервис 1С:Фреш (1cfresh.com) поддерживает стандартный интерфейс OData —
программное чтение данных базы без ручной выгрузки файлов
(официальная статья: https://1cfresh.com/articles/data_odata).

**Настройка в приложении Фреш (один раз):**
1. **Администрирование → Синхронизация данных → Настройки стандартного интерфейса OData**.
2. На вкладке **Авторизация** создать служебного пользователя (ему автоматически даётся роль **УдаленныйДоступOData**).
3. На вкладке **Состав** включить доступ к **регистру бухгалтерии «Хозрасчетный»** и **плану счетов**.

**URL запросов:** `https://1cfresh.com/a/<база>/<id>/odata/standard.odata/…`
(адрес приложения берётся из браузера, без кода языка, например `https://1cfresh.com/a/sbm_demo/1962515`).
Аутентификация — **HTTP Basic** (логин/пароль служебного пользователя).

**Использование (`core/api_client.py`):**
```python
from core.api_client import OneCClient
client = OneCClient("https://1cfresh.com/a/sbm_demo/1962515", "логин", "пароль")
df = client.fetch_osv("2026-01-01T00:00:00", "2026-06-30T23:59:59")  # ОСВ
df.head()
```
- `fetch_osv` — ОСВ через виртуальную таблицу `BalanceAndTurnovers` регистра бухгалтерии; возвращает
  ту же схему, что и файловая ОСВ (готова для `AutoAuditor1C`).
- `fetch_accounting_records` — сырые движения (проводки) регистра за период.
- CLI для живой проверки: `python core/api_client.py <URL> <логин> <пароль> --start ... --end ...`.

**Ограничения 1С:Фреш:** HTTP-заголовок `1C_OData-DataLoadMode` не обрабатывается;
при ограничениях доступа к данным в запрос нужно добавлять `allowedOnly=true`;
ошибка `401` означает неверные логин/пароль или отсутствие роли `УдаленныйДоступOData`.
Тесты клиента (`tests/test_api_client.py`) работают на моках и не требуют доступа к базе.

## Как запустить

```bash
pip install -r requirements.txt
python app/run.py          # Streamlit UI на :8501 (единственный процесс)
```

Или напрямую (без лаунчера):

```bash
python -m streamlit run app/ui.py --server.port 8501
```

Настройки приложения задаются без `.env`:
- доступ к базам и роли — в **`users.json`** (см. ниже);
- список баз для массового аудита — в **`client_databases.json`**;
- одиночное подключение к 1С:Фреш — прямо в форме в боковой панели (URL/логин/пароль);
- пути и порты при необходимости — напрямую переменными окружения (например
  `UI_HOST`, `AUDIT_DB_PATH` — как в Docker).

В боковой панели выберите источник данных: загрузка ОСВ (CSV/XLS/XLSX/HTML) с
опциональным реестром документов, тестовые данные или подключение к 1С:Фреш.
Аудит выполняется локально в том же процессе (без отдельного API-бэкенда).
По клику на строку сводной открывается детализация по счёту (drill-down):
ОСВ по месяцам и аналитика по субконто (для источника 1С:Фреш — через OData,
для файла/тестовых данных — из строк ОСВ с субконто).

## Ограничение доступа, роли и доступ к базам (ТЗ §11)

По умолчанию приложение открыто без входа. Чтобы включить аутентификацию,
задайте пользователей в файле **`users.json`** в корне проекта (см.
`users.example.json`), либо через переменную окружения `AUDIT_USERS`
(обратная совместимость — первый пользователь станет `admin`).

### users.json (рекомендуемый способ)

```json
{
  "admin":   {"role": "admin",      "password_hash": "200000$...$...", "allowed_urls": []},
  "ivanova": {"role": "accountant", "password_hash": "200000$...$...", "allowed_urls": [
      "https://1cfresh.com/a/ab/123"
  ]}
}
```

- Хэш пароля генерируется: `python -m core.auth hash мойПароль` → `200000$<соль>$<хэш>`.
- Роли:
  - `admin` — видит **все** базы и всю историю аудитов;
  - `accountant` — имеет доступ **только к базам, URL которых указаны в
    `allowed_urls`** (сопоставление по URL, регистро/слэшам нечувствительно).
- Файл `users.json` заносится в `.gitignore`/`.dockerignore` — паролей в git нет.

### Поведение доступа
- Режим «🚀 Аудит всех баз» показывает бухгалтеру только его базы (по URL);
  админ — все.
- Одиночный OData-режим («☁️») блокирует бухгалтеру подключение к базе вне его списка.
- Дашборд и сравнение показывают бухгалтеру только его базы и его собственные
  локальные/файловые прогоны; админ видит всё.
- `AUDIT_USERS="логин:хэш,..."` работает как запасной вариант: при пустой БД
  первый пользователь становится `admin`. Если задан `users.json`, он приоритетнее.

### Журнал запусков
Каждый запуск аудита фиксируется в журнале истории с именем пользователя
(колонка `user`); оно показывается в карточке базы на дашборде («Пользователь»).

> **Важно (безопасность):** не храните пароли баз в открытом виде в git.
> `client_databases.json` исключён из репозитория (`.gitignore`) и монтируется
> в Docker как read-only volume, а не копируется в образ.

## Отчеты

По итогам проверки формируются:
- сводный отчет (статус, число флагов, сумма отклонений по видам, рекомендации);
- детальный отчет (тип ошибки, счет, субконто, контрагент, сумма, период, комментарий);
- выгрузка в Excel: первый лист «Обзор» (реквизиты, статус, сводка по проверкам,
  топ крупнейших нарушений), далее полные листы с цветовой индикацией
  (красный/желтый), закрепленной шапкой и автофильтром;
- выгрузка в PDF по принципу «сначала кратко»: статус, сводка по проверкам,
  топ-10 крупнейших нарушений, затем детальные разделы (требует `fpdf2`
  и шрифт DejaVu).

Результаты в интерфейсе можно фильтровать по проверке, счету и контрагенту
(фильтрация только отображения — в выгружаемый Excel/PDF попадает полный отчет).

## Развертывание через Docker

В репозитории есть `Dockerfile`, `docker-compose.yml` и `.dockerignore`.

```bash
# собрать и запустить (порт 8501 — интерфейс)
docker compose up -d --build

# посмотреть логи
docker compose logs -f app

# остановить
docker compose down
```

Приложение доступно на `http://<адрес_сервера>:8501`.
Healthcheck контейнера проверяет эндпоинт Streamlit `/_stcore/health`.

БД SQLite хранится в named volume (`audit_data`), смонтированном как **каталог**
`/app/dbdata` (точка задаётся переменной `AUDIT_DB_PATH`). Монтируется именно
каталог, а не один файл, чтобы WAL-файлы `audit_history.db-wal` и
`audit_history.db-shm` оставались на том же volume и безопасно переживали
перезапуск контейнера. БД работает в режиме WAL (`PRAGMA journal_mode=WAL`) с
`timeout=30` — несколько сессий бухгалтеров могут читать БД параллельно, не
получая «database is locked».

Для доступа по HTTPS/домену поставьте перед контейнером reverse proxy (Caddy, Nginx или
Traefik) и не открывайте порт 8501 наружу напрямую. Обратите внимание: приложение не имеет
аутентификации — ограничьте доступ на уровне прокси, если это публичный сервер.

## Тесты

```bash
pytest
```

Ядро проверок (`core/auditor.py`) и загрузчики (`core/loaders.py`) не зависят от Streamlit
и покрыты тестами (`tests/`), включая реальные выгрузки 1С
(`tests/fixtures/osv_real.xls` — ОСВ по БУ, `tests/fixtures/osv_indicators.xls` — ОСВ с БУ/НУ/БУ-НУ).
Структура: `core/` — ядро аудита, `app/` — приложение (Streamlit UI + лаунчер `run.py`),
`data/` — тестовые данные, `tests/` — тесты.
