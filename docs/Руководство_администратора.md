# Руководство администратора «ИИ-Аудитор 1С»

Для администраторов: пользователи, роли, доступ к базам, конфигурационные
файлы, хранение истории и резервное копирование.

---

## 1. Роли и права

- **`admin`** — видит все базы, всю историю аудитов, может удалять записи без
  ограничений.
- **`accountant`** (бухгалтер) — видит и может проверять **только базы, URL
  которых указаны у него в списке доступа** (`allowed_urls`). Его история —
  собственные прогоны + записи его баз. Без назначенных баз остаются доступны
  только его собственные (локальные/файловые) прогоны.
- Если аутентификация выключена — приложение открыто, доступ как у админа.

## 2. Вход и учётные записи

Вход включается при наличии пользователей в БД (`users` в
`audit_history.db`) или переменной окружения `AUDIT_USERS`
(формат `логин:хэш,логин2:хэш2` — запасной вариант).

Хэш пароля генерируется командой:

```bash
python -m core.auth hash <пароль>
```

Результат: `200000$<соль>$<хэш>` (PBKDF2-HMAC-SHA256). Пароли в открытом виде
нигде не хранятся.

## 3. Управление пользователями

Источник истины для входа — **таблица `users` в БД** (`audit_history.db`).
Основной способ управления — **панель администратора в интерфейсе**
(раздел 3.1). Файл **`users.json`** используется только как **сид первого
запуска**: если таблица `users` пуста, при инициализации она заполняется из
файла. При внесении правок в `users.json` после первого запуска изменения
в действующую БД **не** применяются автоматически.

Формат `users.json` (для первичной загрузки):

```json
{
  "admin":   {"role": "admin",      "password_hash": "200000$...$...", "allowed_urls": []},
  "ivanova": {"role": "accountant", "password_hash": "200000$...$...", "allowed_urls": [
      "https://msk1.1cfresh.com/a/ea/0000000"
  ]}
}
```

- `role`: `admin` или `accountant`.
- `allowed_urls` у админа пустой = «все базы»; у бухгалтера — строгий список.
- Сопоставление URL регистро/слэш-нечувствительно, но **точно по пути** —
  следите, чтобы URL совпадал со значением `url` в `client_databases.json`
  (без лишних сегментов вроде `/en/`).

### 3.1. Панель «👥 Управление пользователями» (рекомендуется)

Видна в сайдбаре **только администратору** (после кнопки «🔓 Выйти»).

- **➕ Добавить пользователя** — логин, роль (Бухгалтер/Администратор),
  пароль (дважды), список доступных баз (по одному URL на строку). Пароль
  хэшируется; запись сразу попадает в БД.
- **✏️ Изменить пользователя** — выбрать пользователя: сменить роль,
  включить/отключить учётную запись (флаг «Учётная запись активна»),
  задать новый пароль (пусто = оставить прежний) и изменить список баз.
  Отключённая учётная запись больше не может войти (проверка `active`
  при аутентификации).
- **🗑️ Удалить пользователя** — только с подтверждением флажком.
- **Защита**: нельзя удалить или отключить **самого себя** и **последнего
  действующего администратора** (система не должна остаться без админа).

Изменения применяются сразу, перезапуск не нужен. История аудитов
пользователя при удалении/отключении **не** удаляется.

### 3.2. Применение правок `users.json` к существующей БД

Если всё же правите файл — примените изменения к действующей БД через
upsert из командной строки (панель делает это сама):

```bash
.venv/bin/python -c "from core.db import upsert_user, get_user; u=get_user('ivanova'); upsert_user('ivanova', u['role'], u['password_hash'], ['https://msk1.1cfresh.com/a/ea/0000000', 'https://msk1.1cfresh.com/a/ea/0000000'])"
```

Права применяются сразу, перезапуск не обязателен.

## 4. Базы для массового аудита: `client_databases.json`

Список баз для режима «📊 Аудит всех баз» — файл **`client_databases.json`**
в корне проекта:

```json
[
  {
    "name": "1;НОВАЯ",
    "url": "https://msk1.1cfresh.com/a/ea/0000000",
    "login": "odata.user",
    "password": "…"
  }
]
```

- `name` может быть задан как `"N;Название"` — номер уходит в первую колонку
  дашборда, в списке баз и колонке «База» видно только название.
- `login`/`password` — учётные данные пользователя 1С:Фреш для OData.
- В массовом режиме реестр документов не загружается (проверки 4.5 и NLP
  недоступны).
- Файл исключён из git и Docker-образа (`.gitignore`/`.dockerignore`) —
  пароли не должны попадать в репозиторий.

## 5. Хранение истории и резервное копирование

- Вся история аудитов хранится в **`audit_history.db`** (SQLite, режим WAL)
  — в таблицах `audits` и `users`.
- Перезапуск приложения **не теряет** историю: она перечитывается из БД.
- Удаление записей происходит **только** через интерфейс
  («🗑️ Управление историей» в дашборде) — по дате, безвозвратно.
- Резервное копирование: копируйте `audit_history.db` **вместе с файлами
  `-wal` и `-shm`** (иначе в копии могут не оказаться последние записи), либо
  делайте консистентную копию через `VACUUM INTO`.
- **Не меняйте** без необходимости переменную `AUDIT_DB_PATH` между запусками:
  другое значение укажет на другой файл, и история «пропадёт» (останется в
  старом файле).

## 6. Переменные окружения (кратко)

| Переменная | Назначение |
|---|---|
| `AUDIT_USERS` | запасной список `логин:хэш` (если нет пользователей в БД) |
| `AUDIT_DB_PATH` | путь к файлу БД (по умолчанию `audit_history.db`) |
| `AUDIT_USERS_CONFIG` | путь к `users.json` (по умолчанию файл в корне) |
| `ONEC_URL` / `ONEC_USER` | URL базы и OData-пользователь 1С по умолчанию |

## 7. Типовые кейсы

- **«Вам не назначено ни одной базы»** у бухгалтера: URL в его `allowed_urls`
  не совпадает с `url` ни одной базы в `client_databases.json` (в т.ч. из-за
  лишнего сегмента `/en/`). Исправьте `allowed_urls` в `users.json` и
  выполните upsert (см. раздел 3).
- **Добавить новую базу**: добавить словарь в `client_databases.json`
  (`name`/`url`/`login`/`password`) и при необходимости выдать доступ
  бухгалтерам через `allowed_urls`.
- **Добавить пользователя**: строка в `users.json` + upsert в БД
  (или создание БД с нуля, если это первичный запуск).

Подробно об интерфейсе — в **«Боковая_панель_справочник.md»** и
**«Руководство_пользователя.md»**.
